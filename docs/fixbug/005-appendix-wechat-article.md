# 别再一种编排打天下了！一文撕开Agent执行模式的真相：ReAct、Chain、Router、Plan&Execute

> 来源：微信公众号 AI认知洞见
> 链接：https://mp.weixin.qq.com/s/4-QFInNM_KObblIymzoxeg

---

你是不是也这样？看到一个Agent框架，拉下来，跑通一个Demo，觉得"哇，真智能"。然后丢到真实业务场景里，结果不是死循环，就是瞎执行，要么慢得像蜗牛。

问题出在哪？因为你还在用同一种"思考-行动"模式，试图解决所有问题。

Agent的世界早就分化了。现在的执行模式，就像汽车有手动挡、自动挡、越野模式、赛道模式一样，选错模式，等于开着一台法拉利去耕田。

今天，我们不和稀泥。直接把这六种执行模式的底裤扒干净——ReAct、Chain、Router、Plan&Execute、Reflection、Parallel。看完你就明白：什么时候该稳，什么时候该野，什么时候该一个人闷头干，什么时候该叫上一群兄弟。

---

## 1. Chain：最稳，也最蠢

**一句话：流水线上的无脑工人。**

你给Chain一张步骤清单，它就像个刚入职的实习生——你说一步，它做一步。做完第一步，绝不多想第二步。做完了，也不回头看一眼。

**典型场面：**

"先查天气，再推荐衣服。"

它就去查天气，然后用这条天气信息推荐衣服。完美。

但如果你说："如果下雨，先查雨衣库存；如果晴天，先查防晒霜。" Chain直接死给你看。

**优点**：稳如老狗。每个步骤都执行，绝不会自己加戏。

**缺点**：蠢如木桩。遇到分支、意外、动态信息，当场瘫痪。

**什么时候用？**

你那破任务真的只有一条直线路径，没有任何"如果……那么……"。比如：每天晚上12点，从数据库拉数据 → 清洗 → 存到另一个表。这种活，Chain就是王者。

**什么时候千万别用？**

任何需要你"看一眼结果再决定下一步"的事。比如一边查资料一边写报告。Chain会像个复读机一样把查到的第一份资料直接塞进报告，不管对不对。

---

## 2. ReAct：混江湖的老油条

**一句话：走一步，看一步，想一步，再走一步。**

ReAct = Reason（推理）+ Act（行动）。它的精髓不是"行动"，而是"在每个行动前动一下脑子"。

它不像Chain那样傻干。它每做一个动作，都会停下来问自己三个问题：

1. 我刚才做了什么？得到了什么结果？
2. 这个结果对我原来的目标意味着什么？
3. 我下一步最该干什么？

**真实场面：**

你问它："帮我找一下张三的联系方式，然后发一封问候邮件。"

它会先想："我需要先找联系方式。" → 行动：搜张三的联系方式 → 看到结果："找到了，是email@xx.com" → 再想："好，现在我有邮箱了，该写邮件了。" → 行动：调用邮件工具发信。

**优点**：贼灵活。半路杀出个程咬金，它能立刻调整。

**缺点**：容易上头。有时候会重复"想-做-想-做"几十次，实际上什么也没干成。而且每一步都要把历史对话塞回上下文，长任务下Token烧得你心疼。

**什么时候用？**

任务中需要不断引入外部信息，而且每一步的下一步都不确定。比如：一个需要查3-5次资料、中间还要做一些简单计算的调研问答。

**什么时候千万别用？**

超过10步的长期任务。ReAct会像一个没地图的人在山里乱转，最后累死。

---

## 3. Router：老板身边的秘书

**一句话：一眼看穿你是什么货色，然后转给最懂你的人。**

Router 自己不干活。它的全部价值就是分类。

用户说一句，Router快速判断：这是售后问题？还是售前咨询？还是闲聊？然后，它把这个问题"啪"地一下甩给对应的专家Agent——售后Agent、售前Agent、闲聊Agent。

**真实场面：**

用户："我上周买的手机开不了机。"
Router："售后类。" → 转给售后Agent。

用户："你们最新款手机多少钱？"
Router："售前类。" → 转给售前Agent。

**优点**：一个入口，N种能力。每个专家Agent可以单独优化，互不干扰。

**缺点**：分类一旦错，全盘输。你明明要退货，它把你分到闲聊组，聊了半天你更火了。

**什么时候用？**

系统需要处理类型完全不同的请求，而且每个类型都有专门的最优处理流程。就像一个大型客服系统。

**什么时候千万别用？**

任务类型单一。用Router就是脱裤子放屁。

---

## 4. Plan & Execute：有图纸的施工队长

**一句话：先画图纸，再搬砖。**

这跟ReAct完全相反。ReAct是走一步看一步，Plan&Execute是先坐下来，把整个路线图画得清清楚楚，然后再开工。

它怎么干？

**第一步**：让LLM生成一个步骤列表。比如"写一份关于碳中和的报告" → 计划：1.查定义 2.查各国政策 3.查企业案例 4.写引言 5.写正文……

**第二步**：执行器按这个列表顺序执行。

**第三步**：如果某一步失败了（比如查不到企业案例），不是瞎调整，而是重新回到计划阶段，生成一个新计划。

**优点**：用户能看到完整进度，心里有底。执行中不会像ReAct那样随时跑偏，因为有图纸约束着。适合长任务（10步以上）。

**缺点**：最初的图纸可能完全脱离实际。比如你计划"先查A再查B"，结果A查完发现B其实不需要查。重计划很贵。一旦中途环境变化，就得重新画图纸。

**什么时候用？**

任务步骤多、依赖关系明确，且环境相对稳定。比如：自动化写行业研究报告、制定旅行计划、生成测试脚本。

**什么时候千万别用？**

任务高度不确定，每走一步都可能推翻之前的假设。那还是用ReAct吧。

---

## 5. Reflection：自己当自己老师的学霸

**一句话：写完作业，自己批改，再交作业。**

Reflection 不是一个独立的执行流程，而是一个质检环节附在其他模式上。

它的做法极其简单粗暴：

1. 用Chain、ReAct或Plan&Execute生成一个初版结果。
2. 换一个身份（甚至用同一个模型，但换一段提示词）来审视这个结果："有什么错误？哪里不严谨？逻辑有没有矛盾？"
3. 把审查意见返回，重新生成修正版。
4. 重复2-3，直到满意。

**真实场面（代码生成）：**

- 初版："用冒泡排序。"
- Reflection："如果数据量超过1000条，冒泡排序效率太低，建议用快速排序。"
- 修正版："用快速排序。"
- Reflection再看："边界条件处理了吗？空数组呢？"
- 再修正。

**优点**：质量肉眼可见地提升。尤其在代码生成、数学解题、逻辑推理这类任务上。

**缺点**：时间翻倍（甚至更多）。因为每次反思都要额外调用模型。

**什么时候用？**

结果正确性比速度重要一千倍的场景。比如：医疗诊断辅助、合同条款生成、高风险的代码生成。

**什么时候千万别用？**

实时聊天。你反思三遍，用户已经摔手机了。

---

## 6. Parallel：三头六臂的怪物

**一句话：能同时干的，绝不排队。**

Parallel 的理念最简单：不相关的子任务，同时执行。

比如用户问："对比一下iPhone 15和小米14的优缺点，再查一下明天北京和上海的天气，最后告诉我今天的新闻头条。"

**如果顺序执行：**

查iPhone 15 → 查小米14 → 查北京天气 → 查上海天气 → 查新闻头条。

总时间 = 5个任务的时间总和。

**如果并行执行：**

同时发起五个查询 → 等最慢的那个返回。

总时间 ≈ 最慢的那个任务的时间。

**优点**：墙钟时间缩短到极致。尤其在网络IO密集型的任务（API调用、数据库查询）上，效果爆炸。

**缺点**：任务之间不能有任何依赖。你不能在查完iPhone之前就去对比，这是矛盾的。

**什么时候用？**

- 需要同时获取多个独立数据源的信息。
- 超参数调优，同时跑多个实验。
- 任何"先有A和B，然后把它们合并"的任务。

**什么时候千万别用？**

步骤之间有明确的数据依赖，比如"先查A，再用A的结果去查B"。用Parallel就是找死。

---

## 别再问"哪个最好"？要问"当前这一步，该用哪种模式"

残酷的真相是：真实业务里，你不会只用一个模式。

一个稍微像样的Agent系统，往往是这样的：

- **Router** 先站在门口，看一眼请求类型，分发给不同的 Plan&Execute 执行器。
- 每个执行器内部，对于独立的数据获取动作，用 **Parallel** 加速。
- 对于每一步不确定的探索性动作，启用 **ReAct**。
- 对于完全固定的子流程（比如从数据库取用户信息），直接用 **Chain** 保证稳定。
- 最后，对于最终答案，再加一道 **Reflection** 质检。

**这叫混合编排。**

你别觉得这很复杂。人类的思考本来就是混合的——你上班时有的任务机械重复（Chain），有的任务要随机应变（ReAct），开大会前你会在脑子里画个提纲（Plan&Execute），同时你还能一边回微信一边写PPT（Parallel）。

Agent不是在模仿机器，而是在模仿人。所以，下次再有人问你"你的Agent用的什么模式"，别再说"我用的是ReAct"或者"我用的是Plan&Execute"了。

**你要说：**

> "我在Router层分流，在长任务上启用Plan&Execute，在执行单元里嵌入ReAct，对IO用Parallel加速，最后用Reflection兜底质量。"

**这才是能打的生产级Agent。**

---

## 选型快查卡

| 你的任务特征 | 直接选这个模式 |
|------------|--------------|
| 步骤固定，无分支 | **Chain** |
| 步骤少，需要边查边思考 | **ReAct** |
| 多类任务混在一起 | **Router** |
| 长流程（>10步），可提前规划 | **Plan&Execute** |
| 结果精度压倒一切 | **Reflection**（叠加使用） |
| 多个独立任务，希望快点跑完 | **Parallel** |

---

## 写在最后：

所有执行模式本质上都是 Chain 的编排。你最先要学会的不是"选模式"，而是理解 Chain 这个底层抽象。

模式的选择根本上是由"**任务是否有完整可预见的步骤图**"决定的：

1. Reflection 和 Parallel 不是模式，是**增强手段**。你可以把它们加到任何模式上。
2. Router 是系统架构层面的分流器，它做的事情和"模式"**正交**。

所以，如果你真的想在生产环境落地一个 Agent，不要问"我该选 ReAct 还是 Plan&Execute"。

**你应该问：**

> "在这个具体任务上，步骤图是已知的还是未知的？步数大概多少？每一步的确定性有多高？"

回答完这个问题，模式自然就浮出水面了。

# Nova 任务系统问题诊断报告

**日期：** 2026-05-07  
**对话：** Jarvis ↔ 先生

---

## 一、问题描述

Nova 的任务派发机制存在三层系统性缺陷，导致：

1. **任务丢失** — 我派了后台任务，先生等不到结果
2. **工具断供** — 低估复杂度后想补救，发现 tools 被收回无法再派
3. **结果断联** — subagent 完成通知跳过主 Agent，直达先生
4. **执行失联** — subagent 从未被真正拉起，tasks.md 只是状态记录

---

## 二、问题根因分析

### 2.1 上游 — 复杂度判断不准

**现状：**
- preflight 只输出 Low/Medium/High 标签
- 只告诉系统"用什么工具"，不告诉我
- 评估无明确规则，靠感觉
- 错误时没有补救通道

**问题：**
- 任务被判定为 Low → 收回 tools → 实际需要多轮调用 → 派不下去 → 任务丢失

### 2.2 执行层 — Agent 模式名存实亡

**现状：**
- `delegate_task` / `delegate_complex_project` 只是写入 `~/.nova/tasks.md`
- 没有任何进程读取并执行这些任务
- subagent 从未被拉起
- Session 结束后任务状态丢失

**问题：**
- 派了等于没派，先生看不到结果

### 2.3 下游 — 通知机制错位

**现状：**
subagent 完成 → notification → TUI/Discord → 先生
                         ↓
                    我（完全不知情）

**问题：**
- 通知绕过主 Agent 直达先生
- 我派出的任务，自己不知道何时完成、结果是什么
- 先生看到结果了，我还在等通知

---

## 三、解决思路

### 3.1 上游 — 复杂度评估 + 工具建议

**改进方向：**
preflight 输出格式改为：
  complexity: Low
  suggested_tool: (self | delegate_task | delegate_complex_project)
  reasoning: "..."

- 不只是给标签，直接告诉**该用什么工具**
- 评估逻辑需要有可解释的规则（而非黑盒）
- 评估错了有补救通道（比如先生确认后降级/升级）

### 3.2 执行层 — 真正的任务队列

**改进方向：**
- delegate 不只是写文件，要真正触发执行
- subagent 拉起机制需要内置到 daemon 中
- 任务状态持久化（跨 Session 保留）
- 可能需要区分不同类型的执行器（快速查询 / 深度调研 / 长时间运行）

### 3.3 下游 — 通知先回主 Agent

**改进方向：**
subagent 完成 → notification → 主 Agent
                                ↓
                           我处理后 → 先生

- notification 先推给我，我决定如何回复/转达
- 或者主 Agent 和先生同时收到（先生可选择）
- 我有权决定：直接转发、补充信息、标记重点

---

## 四、优先级建议

| 层级 | 问题 | 优先级 | 难度 |
|------|------|--------|------|
| 上游 | 评估输出建议工具而非标签 | 高 | 中 |
| 下游 | notification 先回主 Agent | 高 | 低 |
| 执行层 | 任务真正被拉起执行 | 高 | 高 |

**建议先改下游**（通知链路，影响最小、收益最直接），再改上游（评估逻辑），最后改执行层（需要重构调度机制）。
